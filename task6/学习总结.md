## 二、六个被实验"砸实"的认知

### 认知 1：上下文不是背景板，它就是能力本身（Ch.1 消融实验）

实验 1-1 我跑了 5 种上下文模式 × 2 个离线财务任务（共 10 组），结果：

| 模式 | 完成情况 | 行为 |
| --- | --- | --- |
| full（完整上下文） | 完成，平均 4 次工具调用 / 5.3s | 正常 ReAct |
| no_reasoning（去掉思考） | 完成，3 轮 / 4.6s | 简单任务影响不大 |
| no_history（去掉历史） | **两组都跑满 10 轮、30+ 次工具调用，无答案** | 反复做同一操作，死循环 |
| no_tool_calls（去掉工具） | 形式上"完成" | grounding 判定 **ungrounded（编造数字）** |
| no_tool_results（去掉工具结果） | 形式上"完成" | 同样 **ungrounded** |

最震撼的是：**"模型给出了一个看起来完整的回答"和"任务完成了"是两回事。** 看不到工具、看不到执行结果时，模型照样写一份像样的财务结论，但数字全是编的。这就是书里说的——可靠性来自"约束＋验证＋纠正"，而不是模型自觉。

### 认知 2：混合检索不是教条，是被数据逼出来的选择（Ch.3）

实验 3-6 我在同一测试集上分别只跑 BM25、只跑稠密向量、再跑混合：

| 策略 | Recall@3 | MRR |
| --- | --- | --- |
| BM25（jieba 分词） | 0.833 | 0.792 |
| Dense（MiniLM-L6-v2） | 1.000 | 0.917 |
| **Hybrid-RRF** | **1.000** | **1.000** |

实跑中我看清了两者各自的死穴：BM25 怕语义改写和跨语言（问"酒后伤人"，文档写"醉酒"，就漏）；稠密向量怕近重复编码（型号 XR-7003 和 XR-7001 的向量几乎一样，排序会错）。RRF 把两路结果融合，不是为了时髦，而是因为**两种错误恰好不重叠**。

另外实验 3-4 我还因为 Windows 装不了 annoy/hnswlib，用 numpy 手写了 50 棵随机投影树复刻 ANNOY，并与 usearch 的 HNSW 对比：recall 0.99 vs 1.00，而 HNSW 构建快 14 倍、体积小 15 倍、增量插入不用全量重建。亲手算过一遍，"图索引为什么成为主流"不再是结论而是体感。

### 认知 3：Agentic RAG 的本质是"承认一次检索不够"（Ch.3）

实验 3-8 我用同一道多跳法律题（"醉酒后过失致人重伤，且有盗窃前科"）对比两种 RAG：

- **非 Agentic**：单次检索只捞到不适用的条文，然后放弃作答；离线 21372 条法条的整体证据召回仅 **48%**，复杂题只有 **8%**
- **Agentic**（DeepSeek-reasoner，4 轮 16 次检索）：把问题分解，先找到《刑法》§18（醉酒应负刑事责任）、再找到 §235（过失致人重伤），分层组织答案；离线整体召回 **100%**、复杂题 **100%**，平均检索 1.0→1.3 次

我学到的不是"多检索几次"，而是一个工程判据：**当问题需要的证据分散在多个地方时，让 Agent 带着中间结果迭代检索，召回率的提升远大于多花的那点检索成本。**

### 认知 4：多 Agent 买的是可控性，不是省钱（Ch.10）

这是我预期被推翻最狠的一章。以 10-2 书籍翻译为例（Manager＋术语专家＋翻译专家＋审校专家）：

| 指标 | 管理者模式 | 单 Agent |
| --- | --- | --- |
| 主上下文峰值 | **883 tok** | **2101 tok（2.4 倍）** |
| 指定术语遵从率 | **100%** | **27%** |
| 术语内部一致率 | 89% | 78% |
| **全流程总 token** | **14672** | **8293** |

团队总 token 反而更高。多 Agent 的真实收益是：**Manager 的脑子与书长解耦**（书越长，883 vs 2101 越致命）和**术语一致性**（术语表落盘，各翻译只共享文件不共享上下文）。

10-1 的配对对比给了我另一面：弱模型下"共享上下文的角色移交" **0/9** 能收尾，而"上下文隔离的技能调用"有 3/9——模型带着混乱的身份和历史反而草草交差。从此我判断要不要拆 Agent，先问两个问题：**第二个 Agent 能带来什么新信息通道？上下文隔离还是共享？**

10-4 并行网页搜索还让我实测了级联终止：并行 23.5s vs 串行 30.3s（加速 1.285），任一找到即广播一次 terminate，6 个浏览器 context 全部干净关闭。加速比不是重点，**资源不泄漏、消息不重复**才是工程底线。

### 认知 5：没有评估，所有"改进"都是自我感动（Ch.7）

自学加餐时我跑了两个评估实验：

- **7-public-health**：5 个任务 × 6 小题，demo 满分 30/30，19 个测试通过——第一次完整体验"指标体系＋评分细则"怎么把模糊的"答得好不好"变成可核对的数字
- **7-elo**：模拟 5000 场嘈杂的成对比较（8 个模型、平局率 0.1），Bradley-Terry 方法恢复出的排序与预先设定的真值**完全一致**，bootstrap 100 次给出置信区间

而 9-3（Prompt 自动优化）给我的教育最深。我让系统完整跑了 10 个用例（1136 秒、93.7k tokens、52 次任务 Agent＋21 次裁判），生成的候选 Prompt 在边界集上 0/5→1/5 改善，但在 holdout 集上 4/5→3/5 退化——**发布门正确地拒绝了这个"拆东墙补西墙"的候选**。如果没有双集回归和硬性发布门禁，我很可能就因为看到一个数字变好而上线。

### 认知 6：负结果和诚实记录，是工程师的职业底线（全书）

这本书（以及我自己）留下了很多"不漂亮"的结果，我都没有刷绿：

- 5-3 代码解数学题 53.3% vs CoT 36.7%，但 **p=0.125 不显著**，正式结论记为负结果
- 5-4 代码解逻辑题 39.3% vs 纯思考 75.0%，**与正文预期的 90% 相反**
- 10-1 demo 中 Tavily 返回了错误销量（11.9 万辆，实际约 352 万）——机制正常、数据质量问题，原样记录
- 我自己跑测试时遇到的 3 个失败，根因是教程测试用例硬编码了 bash 方言（`false`/`export`），在 Windows 不成立，如实标注为平台差异，而不是改测试凑通过
- 9-9 有 1 个测试因教程 zip 哈希锚点打包错位而失败，与本机无关，同样保留 1 failed

这些经历让我真正认同书里的态度：**实验的价值在于可复核，不在于好看。**

## 三、踩坑实录：21 天里我被现实教训的事

| # | 坑 | 教训 |
| --- | --- | --- |
| 1 | 系统 Python 3.14 与教程不兼容，uv 自带 3.12 才跑通 | 先看版本约束再动手 |
| 2 | 教程默认模型 Qwen3-235B 在平台下架 | 模型名会变，代码要留 provider 适配层 |
| 3 | ch3 整包安装在 Windows 失败（annoy 无 wheel） | 按需装轻量依赖，或手写替代实现 |
| 4 | `.env` 必须在运行目录（load_dotenv 不向上递归） | 配置加载路径要显式验证 |
| 5 | 消融实验默认 PDF 在 GitHub 上国内打不开，白烧 token | 遇到网络不通要立刻停，换离线用例 |
| 6 | Coding Agent 真实任务陷入"死亡螺旋"：连续 13 次重复执行 | 根因是子进程 PATH 解析到 WindowsApps 占位程序（退出码 9009）；修复靠解释器目录前置 PATH＋重复指纹看门狗 |
| 7 | `Tee-Object` 对长任务缓冲，造成"假挂起" | 用 `python -u` ＋ JSON 文件取证 |
| 8 | 我自己写 Mini Agent 时，多轮历史里的旧 tool 结果污染了下一轮判断 | "本轮是否已执行工具"只能看**最后一条消息**，不能看历史里是否出现过 tool |

第 6 和第 8 条特别有意思：一个是教程里的 Agent 在我机器上踩的坑，一个是我自己写的 Agent 踩的坑，根因都是**状态边界没分清**——进程的 PATH 状态、对话的轮次状态。Harness 工程说到底就是在管理这些状态。

## 四、结业作品：把学到的东西写进代码（Mini Agent）

为了证明不是"读了一遍"，我独立写了一个 [共学营学习助手](../mini-agent/agent.py)，一个文件里融合了三章的核心机制：

- **Ch.2 上下文工程**：稳定系统前缀（利于 KV Cache）＋工具定义＋每轮打印状态栏＋长工具结果截断到 1200 字
- **Ch.3 记忆与知识库**：手写 BM25（jieba 分词）直接索引教程 10 章正文；JSON 跨会话长期记忆
- **Ch.4 工具**：OpenAI tool-calling 协议、ReAct 循环；计算器用 AST 白名单沙箱（拒绝 `__import__`、属性访问、大指数）

验证证据：

- **21 个离线测试全部通过**（[pytest_run.txt](../mini-agent/pytest_run.txt)），覆盖检索、记忆持久化、沙箱攻击拦截、ReAct 收尾
- 真实 API（SiliconFlow Qwen3-8B）4 个脚本场景全部正确（[real_run.txt](../mini-agent/real_run.txt)）：
  1. "核心公式是什么" → 检索后记/第 1 章，给出有依据的分层回答
  2. "记住我的学习目标" → 写入长期记忆并返回事实 ID
  3. **新会话**问"我的目标是什么" → 清空对话历史后仍从长期记忆直接回答，不再调工具
  4. "计算 36×0.25" → 计算器返回 9.0

此外我把全书结构做成了一张可交互的[知识地图](../knowledge-map/knowledge_map.html)：10 章核心概念脉络＋109 个实验的编号/状态/说明，并标注了我本人实跑的 30 个及产物位置。

## 五、如果重新来一次，我会怎么做

1. **第一天就先搭评估，再跑实验。** Ch.7 是我后期才补的，如果一开始就有"怎么判断成功"的意识，前期很多对比可以少走弯路。
2. **更早信任离线验证。** 我前期总担心"不调真实 API 算不算数"，后来发现教程大量核心机制（BM25、异步、验证器）用确定性输入就能验证，零费用且可重复。
3. **读代码先读测试和 README，再读主循环。** 教程自己的 LEARNING.md 给的"三层阅读法"（Starter/Builder/Maintainer）我是中途才开始用，效率提升明显。
4. **把每次踩坑立即写进档案。** 我能在 21 天后交出这份全是真实数据的总结，靠的是 memory 档案每天更新，而不是事后回忆。

## 六、最终收获（150 字版）

这 21 天最大的变化，是我从"模型决定论"转向了"工程系统论"：Agent 的可靠性不来自模型多聪明，而来自上下文如何组织、工具如何约束、结果如何验证、错误如何回滚。我亲手跑过历史缺失导致的死循环、拆东墙补西墙被发布门拦截、多 Agent 用更高总成本换来上下文解耦——每一条书上的结论，都在我机器上留下了数据。结业不是终点：我已经能独立设计并验证一个带记忆、检索和工具的 Agent 了。
